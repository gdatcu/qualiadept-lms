### 1.2 A Brief History of Web Automation

#### 2004 – Selenium: The Pioneer

It all started at **ThoughtWorks** in 2004, when engineer **Jason Huggins** got tired of manually testing an internal time-and-expenses app over and over again. He wrote a JavaScript library that "clicked" the buttons on the page by itself: **JavaScriptTestRunner**, later renamed **Selenium Core**. The major problem: the code ran inside the page and ran into browser security rules (Same-Origin Policy).

In parallel, **Simon Stewart** (also at ThoughtWorks, then Google) built **WebDriver**, a project that controlled the browser **from the outside**, using native APIs. In 2011, the two projects merged into **Selenium 2 (Selenium WebDriver)**, and in 2018 the protocol became an **official W3C standard**. Selenium 4 (2021) fully adopted this standard.

#### 2017 – Cypress and Puppeteer: The JavaScript Revolution

As applications became "Single Page Applications" (React, Angular, Vue), Selenium tests became slow and unstable ("flaky"). Two new players appeared almost simultaneously:

* **Cypress** (Brian Mann, Cypress.io) – made a radical decision: the test runs **inside the browser**, in the same run-loop as the application. Result: a spectacular debugging experience (time-travel), but also architectural limits (a single tab, cross-origin limitations, JavaScript/TypeScript only).

* **Puppeteer** (the Chrome DevTools team at Google) – a Node.js library that controlled Chrome directly via the **Chrome DevTools Protocol (CDP)**, fast and precise, but only for Chromium and without its own test runner.

#### 2020 – Playwright: "Puppeteer, but for all browsers"

The engineers who had created Puppeteer at Google moved to **Microsoft** and started from a simple question: *"What if we kept Puppeteer's speed, but supported all browser engines and built a test runner designed specifically for E2E?"* That is how **Playwright** was born (first public release in January 2020, v1.0 in May 2020). In 2021, **@playwright/test**, the official runner, arrived along with **Trace Viewer**, and in 2023 **UI Mode**. The release cadence is roughly one minor version per month.

#### 🧪 E2E Example 1.2 – The Same Scenario Across Three Eras

The scenario: the user adds a task and sees it in the list. Here is what it looks like in each generation of tools:

**📋 Code 1.04** · `📄 Selenium WebDriver (JavaScript)`

```js
const { Builder, By, until } = require('selenium-webdriver');

const driver = await new Builder().forBrowser('chrome').build();
await driver.get('https://tasktracker.qualiadept.eu');
  const input = await driver.wait(
    until.elementLocated(By.css("[data-testid='input-task-name']")), 10000);
  await input.sendKeys('Historical task');
  const btn = await driver.findElement(By.css("[data-testid='submit-task-btn']"));
  await driver.wait(until.elementIsEnabled(btn), 10000);   // manual wait
  await btn.click();
  const list = await driver.findElement(By.css("[data-testid='task-list']"));
  await driver.wait(until.elementTextContains(list, 'Historical task'), 10000);
  await driver.quit();
```

### 1.3 Architecture Under the Hood: Who Talks to the Browser and How?

This is the most important theoretical section of the session. The differences in speed and stability between tools do not come from "magic", but from the **communication channel** between the test and the browser.

![Figure 1.2 – The three architectural models: WebDriver (HTTP), In-Browser (Cypress), and WebSocket + native protocols (Playwright)](/images/sessions/premium/session-9/image2.png)

*Figure 1.2 – The three architectural models: WebDriver (HTTP), In-Browser (Cypress), and WebSocket + native protocols (Playwright)*

#### Selenium WebDriver – "The Registered Letter"

Every command in the test (`click`, `sendKeys`, `findElement`) becomes a **separate HTTP request** (JSON format) sent to an intermediary program called a **driver** (`chromedriver`, `geckodriver`, `msedgedriver`). The driver translates the command for the browser and sends back a response. A 200-step test means hundreds of HTTP round-trips. Moreover, Selenium does not natively "know" whether an element is ready for interaction: the engineer must manually write `WebDriverWait` / `ExpectedConditions`.

#### Cypress – "The Spy on the Inside"

The test is injected into an `iframe` in the same tab as the application, while a Node.js server acts as a proxy. Advantage: direct access to the DOM, network, and application state, with no network latency. Disadvantage: being "trapped" inside the tab, Cypress cannot natively control multiple tabs or windows, and its commands use their own model (`cy.get().click()` chains rather than classic `async/await`).

#### Playwright – "The Permanently Open Phone Line"

The test runner (Node.js) opens **a single persistent WebSocket connection** to the Playwright server, which talks to browsers through their native protocols (CDP for Chromium; dedicated protocols for specially built Firefox and WebKit binaries). Commands and events flow in both directions in real time. Three superpowers come from this:

* **Auto-waiting**: before every action, Playwright automatically checks that the element is attached to the DOM, visible, stable (not animating), enabled, and receiving events (not covered by a pop-up).

* **Browser Contexts**: a context is like a separate "incognito" profile, created in milliseconds. Every test gets its own clean context—zero inherited cookies or localStorage.

* **True cross-browser**: the same test runs on Chromium, Firefox, and WebKit (Safari's engine), on Windows, macOS, and Linux.

#### 🧪 E2E Example 1.3 A – Auto-Waiting in Action

The list comes from the network, and the button changes state based on the input. The test contains no fixed pauses:

```ts
test('Playwright automatically waits for data and the button', async ({ page }) => {
```

#### 🧪 E2E Example 1.3 B – Isolation via Browser Context

**📋 Code 1.09** · `📄 tests/01-context-isolation.spec.ts`

```ts
import { test, expect } from '@playwright/test';

test('two contexts do not share state', async ({ browser, baseURL }) => {
    const contextA = await browser.newContext({ baseURL });

    const contextB = await browser.newContext({ baseURL });

    const pageA = await contextA.newPage();

    const pageB = await contextB.newPage();

    await pageA.goto('/');

    await pageA.evaluate(() => localStorage.setItem('user', 'Ana'));

    await pageB.goto('/');

    const valueA = await pageA.evaluate(() => localStorage.getItem('user'));

    const valueB = await pageB.evaluate(() => localStorage.getItem('user'));

    expect(valueA).toBe('Ana');

    expect(valueB).toBeNull();      // context B is a separate "incognito profile"

    await contextA.close();

    await contextB.close();
});
```

* **A.** `isVisible()` responds immediately, without waiting. If the GET request hasn't finished yet, the spinner is visible and the test fails. You will see green and red runs mixed together—a flaky test. The web-first assertion `toBeHidden()` retries for up to 5 seconds and eliminates the issue.

**📋 Code 1.11** · `📄 tests/01-cookie-isolation.spec.ts`

```ts

test('a cookie in context A does not reach context B', async ({ browser, baseURL }) => {
    const contextA = await browser.newContext({ baseURL });

    const contextB = await browser.newContext({ baseURL });

    await contextA.addCookies([{ name: 'theme', value: 'dark', url: 'https://tasktracker.qualiadept.eu' }]);

          expect(await contextA.cookies()).toHaveLength(1);

          await contextB.close();
      });
```

* **C.** The order differs from run to run because tests run in parallel, in separate processes (workers). Conclusion: every test must be independent and must not rely on execution order.

### 1.4 Direct Comparison

| Criterion | Selenium | Cypress | Playwright |
| ----- | ----- | ----- | ----- |
| Release year / author | 2004 · ThoughtWorks (now open-source community) | 2017 · Cypress.io | 2020 · Microsoft |
| Languages | Java, Python, C\#, Ruby, JavaScript, and more | JavaScript / TypeScript | TypeScript / JavaScript, Python, Java, .NET |
| Browsers | Chrome, Firefox, Edge, Safari (real installed browsers) | Chrome family, Edge, Firefox; experimental WebKit | Chromium, Firefox, WebKit (+ branded Chrome / Edge) |
| Communication | HTTP (W3C WebDriver) via driver | Runs inside the browser, next to the app | Persistent WebSocket + CDP / native protocols |
| Auto-waiting | Not native (explicit waits) | Yes (command retries) | Yes (actionability checks) + web-first assertions |
| Multi-tab / windows / iFrames | Yes (with switchTo) | Limited (single tab) | Yes, native |
| Parallelization | Via Selenium Grid / framework | Paid / via external services | Native, free (`workers`, `fullyParallel`, `shard`) |
| Included test runner | No (JUnit, TestNG, pytest, etc.) | Yes | Yes (`@playwright/test`) |
| Debugging | Logs, manual screenshots | Time-travel in Test Runner | Trace Viewer, UI Mode, Inspector, Codegen |
| Mobile | Native via Appium | Viewport only | Device emulation (viewport, touch, user agent) |

### 1.5 When Do You Choose Each Tool?

A mature engineer is not a "fan" of any tool, but chooses based on context. Selenium remains the backbone of many corporations (banking systems with thousands of Java tests, mobile testing via Appium). Cypress is loved by frontend teams for component testing. For a **new** web E2E testing project with TypeScript, CI/CD, and cross-browser requirements, Playwright is the market's default choice.

### 1.6 💡 Did You Know...?

::: tip 💡 Did you know… The name Selenium is a joke
At the time, the most popular commercial testing tool was made by Mercury Interactive. Jason Huggins remarked that selenium is the antidote for mercury poisoning. The name stuck. Playwright means "a writer of plays": the one who writes the script that the actors (browsers) perform on stage. That is why the logo features theater masks, and test files are called "spec" (specifications of the scene). Playwright surpassed Cypress in weekly npm downloads back in 2024, and by early 2026 the gap had reached roughly 30 million versus 6.5 million downloads per week. Playwright's WebKit runs on Windows too: you can verify Safari's engine behavior without owning a Mac. In November 2026, Playwright reached version 1.65, which even added support for the Bun runtime in the test runner.
:::

### 1.7 📖 Applied Story: "The Three Couriers"

::: info 📖
You need to deliver 100 packages (commands) in an office building (the browser). Courier Selenium is a reliable person who speaks every language (Java, Python, C\#). For each package, however, they go to the front desk (the driver), fill out a form (the HTTP request), wait for confirmation, and only then head upstairs. If the office door is closed (the element isn't ready), they return with the package and report an error—unless you explicitly told them "wait 10 seconds at the door." Courier Cypress got hired directly by the company inside the building. They have access to all offices on their floor and see everything in real time. But they aren't allowed to leave the building (another domain) and cannot open a second building (a second tab). Courier Playwright has a permanently open radio line with every building in the city (Chromium, Firefox, WebKit). Before knocking on a door, they automatically check if someone is inside and if the door is clear (auto-waiting). Most importantly, they can dispatch 10 colleagues in parallel, each with their own access key (Browser Context), without getting in each other's way.
:::

Let's look inside the generated test file. Recognize the syntax? It's the exact `async/await` from Session 5 and typing from Session 7:

**📋 Code 2.06** · `📄 tests/example.spec.ts`

```ts
import { test, expect } from '@playwright/test';

test('has title', async ({ page }) => {
    await page.goto('https://playwright.dev/');

      // Expect the title to contain the substring "Playwright"

      await expect(page).toHaveTitle(/Playwright/);
  });

  test('get started link', async ({ page }) => {
      await page.goto('https://playwright.dev/');

        await page.getByRole('link', { name: 'Get started' }).click();

        await expect(page.getByRole('heading', { name: 'Installation' })).toBeVisible();
    });
```

Four new concepts that we will dive deeper into in upcoming sessions:

* `test(title, callback)` – defines a test case. The callback is an **async** function.

* `{ page }` – a **fixture**: Playwright automatically "injects" a real `Page` object (the one we simulated with an interface in S8), created inside a clean Browser Context.

* `expect(...)` – **web-first** assertions: automatically retry for up to 5 seconds (by default) until the condition becomes true.

* `page.getByRole(...)` – a modern **locator** based on the accessibility role (Session 11).

### 2.4 Playwright Browsers

Playwright does **not** use your personal Chrome; instead, it downloads its own builds, tested and versioned alongside each release:

* **Chromium** – the open-source engine behind Chrome and Edge.

* **Firefox** – a slightly modified Firefox build for automation.

* **WebKit** – the engine behind Safari, compiled for Windows and Linux as well.

Browsers are installed in a global cache (on Windows: `%USERPROFILE%\AppData\Local\ms-playwright`), not inside the project. That's why, after every update of the `@playwright/test` package, you need to run `npx playwright install` again—otherwise you'll get the error *"Executable doesn't exist… Looks like Playwright was just updated"*.

**📋 Code 2.09** · `📄 Terminal`

```bash
npx playwright install            # all browsers
npx playwright install chromium   # Chromium only
npx playwright install --with-deps  # + system libraries (Linux / CI)
npx playwright --version          # installed Playwright version
```

::: tip 💡
"Branded" browsers: If you want to test on real Google Chrome or Microsoft Edge (the ones installed on your computer), you can configure them as `channel: 'chrome'` or `channel: 'msedge'` in `projects` (Chapter 3.4).
:::

### 2.6 💡 Did You Know...?

::: tip 💡 Did you know… Same `{ page }`, different universe
Every test gets its own Browser Context. If test 1 logs in, test 2 still starts logged out. This isolation is the reason Playwright tests can run in any order. `npx` stands for "npm execute": it looks for the command first in the project's `node_modules/.bin`. That's why `npx playwright` uses the exact version from `package.json`, not a global one. A single `example.spec.ts` file = 6 executions: the number of runs is *tests × projects*. A suite of 100 tests across 3 browsers and 2 mobile devices means 500 executions. That's why native parallelization is vital. The HTML report is a static web app: the `playwright-report/` folder can be published as a CI artifact (Session 19) and opened by anyone without Playwright installed.
:::

### 3.3 Global Options: WHAT We Run and HOW the Runner Behaves

| Option | Typical Value | What It Does and Why It Matters for QA |
| ----- | ----- | ----- |
| `testDir` | `'./tests'` | The folder where Playwright looks for tests. |
| `testMatch` | `'**/*.spec.ts'` | The pattern of files treated as tests (default `*.spec` and `*.test`, `.ts`/`.js`). |
| `timeout` | `30_000` | Maximum time for ONE test, in milliseconds. Default is 30 seconds. |
| `expect.timeout` | `5_000` | How long a web-first assertion retries. Default is 5 seconds. |
| `fullyParallel` | `true` | Runs tests within the same file in parallel as well, not just files across workers. |
| `workers` | `undefined` / `1` / `'50%'` | Number of parallel worker processes. Default: half of the logical CPU cores. |
| `retries` | `process.env.CI ? 2 : 0` | How many times a failed test is retried. Locally 0 (you want to see the failure), in CI 2. |
| `forbidOnly` | `!!process.env.CI` | Fails the pipeline if someone left a `test.only` in the code. |
| `reporter` | `'html'` or `[['list'], ['html']]` | Report format: `list`, `line`, `dot`, `html`, `json`, `junit`, `blob`, `github`. |
| `outputDir` | `'test-results'` | Where traces, screenshots, and videos are saved. |

::: warning ⚠️
Retries are not a fix for unstable tests. A test that only passes on the second attempt is marked as **flaky** in the report. Retries help prevent a transient network glitch from blocking the pipeline, but every flaky test must be investigated (Session 17). Do not bump `retries` to 5 to "hide" a bug.
:::

#### 🧪 E2E Example 3.3 – Three Levels of Timeout

**📋 Code 3.09** · `📄 tests/03-timeouts.spec.ts`

```ts

});
```

### 3.4 The `use` Block: HOW the Robot Interacts with the App

Everything you put inside `use` becomes the default value for every test: browser, context, and page options.

| Option | Example | Explanation |
| ----- | ----- | ----- |
| `baseURL` | `'https://tasktracker.qualiadept.eu'` | Enables `page.goto('/')`. Relative URLs are resolved against `baseURL`. |
| `testIdAttribute` | `'data-testid'` | The attribute used by `getByTestId()`. Default is already `data-testid`; change it if your team uses `data-qa` or `data-test`. |
| `headless` | `true` | Runs without a visible window (default). Locally you can pass `--headed`. |
| `viewport` | `{ width: 1280, height: 720 }` | Window dimensions. |
| `trace` | `'on-first-retry'` | Records the test's "black box": DOM, network, console, steps. Other values: `'off'`, `'on'`, `'retain-on-failure'`. |
| `screenshot` | `'only-on-failure'` | Automatic screenshot on failure (`'off'`, `'on'`, `'only-on-failure'`). |
| `video` | `'retain-on-failure'` | Keeps video only for failed tests (`'off'`, `'on'`, `'on-first-retry'`). |
| `actionTimeout` | `10_000` | Maximum time for a single action (`click`, `fill`). Unlimited by default (bounded only by the test timeout). |
| `navigationTimeout` | `15_000` | Maximum time for `page.goto()` and navigations. |
| `locale` / `timezoneId` | `'ro-RO'` / `'Europe/Bucharest'` | Browser language and time zone—critical when testing calendar dates. |

**📋 Code 3.11** · `📄 Example: the use block for Task Tracker`

```ts

  baseURL: 'https://tasktracker.qualiadept.eu',
  testIdAttribute: 'data-testid',   // the attributes we added in Session 6
```

### 3.6 `webServer`: AGAINST WHICH Application (Auto-Starting a Local SUT)

The course application is hosted at `https://tasktracker.qualiadept.eu`, so you **do not need** `webServer` for it: `baseURL` is enough. ### 3.8 💡 Did You Know...?

::: tip 💡 Did You Know...?
`testIdAttribute: 'data-testid'` is already the default value. Many engineers write it explicitly as living documentation: anyone opening the config immediately understands the team's convention. If your frontend team uses `data-qa`, this is the only line you change. A trace is like an airplane "black box": a `trace.zip` file contains DOM snapshots for every step, network requests, console logs, and the test source code. You open it with `npx playwright show-trace` or at trace.playwright.dev, directly in the browser. You can also have multiple configs: `npx playwright test --config=playwright.smoke.config.ts`. Some teams keep a separate config for fast smoke tests and another for the full nightly regression suite.
:::

### 3.9 📖 Applied Story: "The Pilot's Control Panel"

::: info 📖
Your tests are the passengers. `playwright.config.ts` is the cockpit. Before takeoff, the pilot does not reconfigure the plane for each passenger. They set the destination once (`baseURL`), the maximum altitude and flight time (`timeout`), how many runways to use simultaneously (`workers`), the alternate route if the weather turns bad (`retries`), and turn on the black box (`trace`), which records everything in case of an incident. `projects` are the different aircraft in the fleet (Chromium, Firefox, WebKit) flying the exact same route. When the destination airport is right on your own runway (a local app), `webServer` is the control tower: no takeoff until the app confirms it is open.
:::

### 3.10 🧠 Interview Challenge (Technical Question)

::: info 📝 The Interviewer
"What is the difference between `timeout`, `expect.timeout`, and `actionTimeout` in Playwright? A test fails with 'Test timeout of 30000ms exceeded'. What do you check?"
:::

**Your Engineer's Answer:** *"They are three different levels. `timeout` is the total time budget for a single test (default 30 seconds), including fixtures. `expect.timeout` is how long a single web-first assertion keeps retrying (default 5 seconds). `actionTimeout` caps a single action such as `click` or `fill` (unlimited by default, so effectively capped by the test timeout). If a test exceeds 30 seconds, I don't immediately raise the timeout: I open the trace and look for the stuck step. Usually, a click is waiting for an element that never becomes actionable—it's covered by a pop-up (like Chaos Mode from Session 6), it's disabled, or the locator doesn't match. I set a reasonable `actionTimeout` so the error surfaces quickly and points straight to the problematic action."*

### 3.11 🤖 Engineer Mindset in the AI Era: The "Bloated" Config

::: warning 🛡️
QA vs. AI: Nonexistent options and dangerous settings. **The Trap:** Ask an AI for a "complete" `playwright.config.ts` and you will often get dozens of options: some useless, others invented (hallucinated) or borrowed from other tools (for example `defaultCommandTimeout`, which is a Cypress option). You will also frequently see `retries: 3` everywhere or `timeout: 120000`, which mask real problems. **How a QA Engineer Thinks:** Every line in the config must have a justification. The engineer keeps the config minimal, verifies options against the official documentation (or lets TypeScript validate them through `defineConfig`), and prompts the AI specifically: *"Generate a Playwright Test config for a static app hosted at https://tasktracker.qualiadept.eu, with baseURL from the BASE_URL environment variable, trace on-first-retry, screenshot only-on-failure, and 3 desktop projects. Explain each option in a comment."* **Your Market Value:** The config is the highest-impact code in the entire framework: one wrong line affects every test. The engineer who understands it line by line is the one who owns the framework.
:::

### 4.3 Filtering and Selection

As your suite grows from 5 to 500 tests, you will no longer run everything on every change. Playwright gives you several filtering "sieves":

| Command | What It Does |
| ----- | ----- |
| `-g "add task"` or `--grep` | Runs only tests whose title matches the text / regular expression. |
| `--grep-invert "@slow"` | Excludes tests that match. |
| `--grep @smoke` | Runs tests labeled with the `@smoke` tag. |
| `--last-failed` | Re-runs only tests that failed in the previous run. |
| `--only-changed` | Runs tests from files changed compared to Git. |
| `--list` | Lists the tests that would run, without executing them. |
| `--repeat-each=10` | Runs each test 10 times—hunting for flaky tests. |
| `-x` or `--max-failures=1` | Stops on the first failure. |

Tags are added directly in the test definition:

**📋 Code 4.05** · `📄 tests/task-tracker.spec.ts`

```ts
test('page loads', { tag: '@smoke' }, async ({ page }) => {
    await page.goto('/');

    await expect(page).toHaveTitle(/Task Tracker/);
});

test(
  'deleting a task over the network',
  { tag: ['@regression', '@slow'] },
  async ({ page }) => {
    // ...
  }
);
```

::: warning ⚠️
`test.only` and `test.skip`: In code you can use `test.only(...)` to temporarily run a single test and `test.skip(...)` to skip one. A forgotten `test.only` in the codebase would cause CI to run only 1 test out of 500, making the pipeline look "green". That is why the config has `forbidOnly: !!process.env.CI`: in CI, a forgotten `test.only` fails the run immediately.
:::

### 4.9 🧠 Interview Challenge (Technical Question)

::: info 📝 The Interviewer
"A test fails in CI about once every 10 runs, but locally it always passes. Walk me through, command by command, how you investigate it."
:::

**Your Engineer's Answer:** *"First, I download the CI artifacts and open the failed test's trace with `npx playwright show-trace` to see the exact step, DOM state, and network traffic at the moment of failure. Next, I try to reproduce the CI conditions locally: headless, with multiple workers, repeated many times—`npx playwright test -g "test name" --repeat-each=30 --workers=4`. If it only fails in parallel, I suspect shared test data between tests. If it only fails on a specific browser, I filter with `--project`. Once reproduced, I use `--debug` or UI Mode to pinpoint the root cause: a random pop-up, a non-web-first assertion, or a slow API response. I do not 'fix' the issue by increasing `retries`."*

### 5.1 What Is Codegen?

**Codegen** (Code Generator) is a recorder: it opens a browser, "watches" what you do (clicks, text inputs, selections), and writes the equivalent Playwright code in real time. It is the fastest way to learn the syntax and get a first draft for a new flow.

![Figure 5.1 – From recording to production code: step 6 is the engineer's responsibility](/images/sessions/premium/session-9/image11.png)

*Figure 5.1 – From recording to production code: step 6 is the engineer's responsibility*

**How does Codegen choose locators?** For each element you interact with, the generator analyzes the DOM and looks for the most robust **unique** locator. The order of preference is: the test attribute (`data-testid`, via `getByTestId`), then the accessibility role with its accessible name (`getByRole`), then the label, placeholder, text, and, only as a last resort, CSS selectors. If the locator it finds matches multiple elements, the generator refines it until it becomes unique.

::: tip 🏆
The payoff for your work in Session 6: Because in Session 6 you added `data-testid` to the input, the button, the list, and the error message, Codegen will generate locators like `getByTestId('input-task-name')` for your app – stable, short, and independent of CSS and text. On an app without test attributes, the exact same click would have produced something fragile, such as `locator('div:nth-child(3) > form > button')`.
:::

#### 🧪 E2E Example 5.1 – Locator Preference Order on Task Tracker

Not every element in the application has a `data-testid`. For those elements, Codegen moves down the preference order:

**📋 Code 5.01** · `📄 tests/05-locator-priority.spec.ts`

```ts
import { test, expect } from '@playwright/test';

test('locators that Codegen would choose', async ({ page }) => {
    await page.goto('/');

    // 1. Has data-testid -> highest priority

    await expect(page.getByTestId('task-list')).toBeVisible();

    // 2. No data-testid, but has an accessibility role (h1) -> getByRole

    await expect(page.getByRole('heading', { name: 'QA Task Tracker' })).toBeVisible();

    // 3. No relevant role (a plain span) -> visible text

    await expect(page.getByText('API Online')).toBeVisible();
});
```

### 5.5 From Raw Code to Production Code

Codegen did a great job with the locators. As an engineer, however, you immediately spot five problems:

| Problem in raw code | Why it is dangerous |
| ----- | ----- |
| `test('test', ...)` | The title says nothing. In the report and in CI, nobody will know what failed. |
| Absolute URL `https://tasktracker.qualiadept.eu/` | The test is tied to a single environment: it cannot run against your local app or another instance. It needs `page.goto('/')` + `baseURL`. |
| Hardcoded click on `close-promo-btn` | The Chaos pop-up always appears, but at a **random** time (between 2 and 6 seconds). A fixed step makes the test dependent on the recording timing: either it waits unnecessarily up to 6 seconds, or the overlay appears before the close step and intercepts the click on Save. On an environment where the promo is disabled, the step fails with a timeout. |
| Redundant click on the input before `fill` | `fill()` focuses the element automatically. It is noise. |
| Click on "delectus aut autem" | An accidental click on a task (the data comes from an API and can change). It can even trigger the `.completed` toggle. |

#### ❌ DON'T Do This (Codegen code pushed straight into the repository)

The code above, unmodified, would only pass code review on a team without standards. It will be slow or flaky because of the pop-up and will not work on another environment.

#### ✅ DO This (Code refactored by an engineer)

**📋 Code 5.10** · `📄 tests/task-tracker.spec.ts (after refactoring)`

```ts
import { test, expect } from '@playwright/test';

test.describe('Task Tracker – add task', () => {
    test.beforeEach(async ({ page }) => {
        // The Chaos pop-up appears at a random time (2-6 s):

        // we close it automatically whenever it shows up during the test.

        await page.addLocatorHandler(page.getByTestId('close-promo-btn'), async (btn) => {
            await btn.click();
        });

        await page.goto('/');                       // baseURL from playwright.config.ts
    });

    test('user adds a new task and sees it in the list', async ({ page }) => {
        const taskName = 'Codegen Testing';

        await page.getByTestId('input-task-name').fill(taskName);

        await page.getByTestId('submit-task-btn').click();

        await expect(page.getByTestId('task-list')).toContainText(taskName);
    });
});
```

What we changed and why:

* **Descriptive title** + `test.describe` to group scenarios belonging to the same feature.

* `page.goto('/')` – relies on `baseURL`, so the exact same test runs on any environment.

* `page.addLocatorHandler(...)` – a "guard" that closes the pop-up **only when it appears**, before any action. The test becomes deterministic.

* We removed redundant or accidental clicks.

* Test data lives in a variable (`taskName`) – the first step toward Data-Driven Testing (Session 14).

### 5.6 Limitations of Codegen: When NOT to Rely on It

* **It does not understand business intent.** It records what you do, not what *should* be verified. You have to add the meaningful assertions yourself.

* **It does not generate logic:** no loops, conditionals, parameterized data, or API setup.

* **It records mistakes too:** accidental clicks, redundant steps, random pop-ups.

* **It hardcodes URLs and data** that change across environments.

* **It knows nothing about your architecture:** it does not use your POM, fixtures, or helpers.

* **It is a draft, not a deliverable.** The rule on mature teams: no Codegen output enters `main` without refactoring and code review.

### 5.8 📖 Applied Story: "The Stenographer and the Editor"

::: info 📖
Codegen is an extraordinarily fast stenographer. It writes down absolutely everything you say in a meeting, word for word, including "umm", jokes, and half-finished sentences. The transcript is 100% faithful, yet nobody would publish it as-is in a newspaper. You are the Editor. You take the transcript, keep the essential ideas (business actions), strip out the noise (redundant clicks), give the article a clear headline (the test name), fact-check everything (assertions), and make sure the piece still makes sense tomorrow in a different context (baseURL, variable data). The stenographer makes you 10x faster; the Editor makes the article publishable.
:::

### 5.9 🧠 Interview Challenge (Technical Question)

::: info 📝 The Interviewer
"If Playwright Codegen generates tests automatically, why do we still need QA Automation Engineers? Can't we just have a manual tester record all the flows?"
:::

**Your engineer answer:** *"Codegen generates code for actions, not a test framework. A suite recorded by a manual tester would have hardcoded URLs, static data, no business assertions beyond what was explicitly clicked, duplicated code across hundreds of files, and random steps that produce flaky tests. At the first UI change, hundreds of tests would have to be re-recorded. My role is to design the architecture (config, POM, fixtures, test data), decide what gets verified and at what layer (UI or API), and integrate everything into CI/CD. I use Codegen as an accelerator – for locators and a first draft – but the code that enters the repository is refactored, reviewed, and aligned with the team's architecture."*

### 5.10 🤖 Engineer Mindset in the AI Era: Codegen + AI = Speed, Engineer = Quality

::: warning 🛡️
QA vs. AI: Code generators do not take ownership. What tools do well: Codegen picks excellent locators because it sees the real DOM. AI assistants are great at refactoring: you hand them raw code and get back a nicely formatted test. On top of that, Playwright now offers MCP (Model Context Protocol) integrations, allowing AI agents to control a Playwright browser directly. The trap: The "record with Codegen + ask AI to clean it up" combo can produce code that *looks* professional while hiding the exact same problems: AI might "fix" the random pop-up with `{ force: true }`, `waitForTimeout(3000)`, or an empty `try/catch` – the exact anti-patterns that mask real bugs. How a QA engineer thinks: Use a prompt with explicit rules: *"Refactor this Codegen code: descriptive title, `page.goto('/')` with baseURL, remove redundant clicks, handle the `close-promo-btn` pop-up with `page.addLocatorHandler`, no `force: true`, no `waitForTimeout`, no empty `try/catch`, web-first assertions."* Then verify the result by running the test 20 times (`--repeat-each=20`). Your market value: In 2026, generating test code is cheap. What is valuable is trust in the test suite. The engineer who can guarantee that a green test means "the application works" – not "the test was tricked into passing" – is the profile companies are looking for.
:::

#### A6. Chaos Mode – Testing the Pop-up Itself

Here we do **not** close the pop-up automatically: it is the actual subject of the tests. So that we don't wait up to 6 real seconds or rely on luck, we use **`page.clock`**: we install a clock controlled by the test, then "jump" 6 seconds forward in page time with `fastForward`. The random timer in `app.js` fires immediately, and the test becomes deterministic.

**📋 Code 8.11** · `📄 tests/task-tracker/chaos-popup.spec.ts`

```ts
import { test, expect } from '@playwright/test';
import { closePromoAutomatically } from '../helpers/chaos';

test.describe('Task Tracker – Chaos mode (promotional pop-up)', () => {
    test.beforeEach(async ({ page }) => {
        await page.clock.install();          // page time is controlled by the test

        await page.goto('/');

        await expect(page.getByTestId('task-list').locator('.task-item')).toHaveCount(5);
    });

    test('pop-up appears within at most 6 seconds', async ({ page }) => {
        await page.clock.fastForward(6_000);

        const overlay = page.getByTestId('promo-overlay');

        await expect(overlay).toBeVisible();

        await expect(overlay).toContainText('Ofertă Specială');
    });

    test('"No, thanks" button closes the pop-up', async ({ page }) => {
        await page.clock.fastForward(6_000);

        await page.getByTestId('close-promo-btn').click();

        await expect(page.getByTestId('promo-overlay')).toHaveCount(0);
    });

    test('without a handler, the pop-up blocks clicking Save', async ({ page }) => {
        await page.clock.fastForward(6_000);

        await expect(page.getByTestId('promo-overlay')).toBeVisible();

        await page.getByTestId('input-task-name').fill('Am I blocked?');

        // The overlay intercepts the click: the action times out after 2 seconds
        await expect(page.getByTestId('submit-task-btn').click({ timeout: 2_000 })).rejects.toThrow();
    });

    test('with addLocatorHandler, the add-task flow succeeds', async ({ page }) => {
        await closePromoAutomatically(page);

        await page.clock.fastForward(6_000);

        await page.getByTestId('input-task-name').fill('Getting past the pop-up');

        await page.getByTestId('submit-task-btn').click();

        await expect(page.getByTestId('task-list')).toContainText('Getting past the pop-up');
    });
});
```

::: info 🔍
**Why does `fill` work while `click` fails?** Before a `click`, Playwright also checks whether the element receives pointer events—that is, whether it isn't covered by another element. `fill` writes directly into the input after checking visibility and editability, so it isn't blocked by the overlay. You can see this difference in the trace error message too: `"... intercepts pointer events"`.
:::

### 8.9 🧠 Interview Challenge (Technical Question)

::: info 📝 The Interviewer
"Your application displays a promotional banner at a random time. How do you write stable E2E tests for the rest of the application, and how do you test the banner itself?"
:::

**Your engineer's answer:** *"I separate the two concerns. For the rest of the application, the banner is noise, so I register a `page.addLocatorHandler()` on its close button. Playwright closes it automatically whenever it appears, before any action or assertion, without `waitForTimeout` and without `force: true`. For the banner itself, I write separate tests where I eliminate randomness: I install `page.clock` before loading the page and advance time with `fastForward`, so the banner appears exactly when I want. I verify that it appears, that it closes properly, and that without a handler it blocks clicks. That gives me deterministic tests for behavior that is random in production."*

### 8.10 🤖 Engineering Mindset in the AI Era: Generated Suites, Verified by You

::: warning 🛡️
**QA vs. AI: "Write me 50 tests for this site"** — **What AI does well:** It can generate dozens of tests in seconds for a public app like SauceDemo, because it has seen it many times in its training data. **The trap:** For that exact reason, it often uses outdated locators (from older versions of the site), invented text, or assertions that always pass—for example `expect(list).toBeVisible()` after an operation that was supposed to modify the list. Worse still, for your own app (Task Tracker), it has no way of knowing the IDs, labels, or business rules. **How a QA engineer thinks:** Give the AI the real context: the page HTML, the config, and an existing test file as a style reference. Ask for precise business assertions (row count, exact text, network requests). Run every generated test multiple times (`--repeat-each=10`) and break it on purpose (for example, change the expected text) to verify that it can fail. A test that cannot fail tests nothing. **Your value in the market:** Teams don't lack generated tests—they lack tests they can trust. The engineer who can prove, with traces and repeated runs, that a suite is stable and meaningful becomes the go-to person for quality on the team.

Turn the login tests into a single parameterized test for `standard_user`, `problem_user` (both reach the products page), and `locked_out_user` (gets an error).

**🗝️ Solution L3**   *(try it yourself before reading)*

**📋 Code 8.17** · `📄 tests/saucedemo/login-data-driven.spec.ts`

```ts
import { test, expect } from '@playwright/test';

type LoginCase = { username: string; succeeds: boolean };

const cases: LoginCase[] = [
  { username: 'standard_user', succeeds: true },
  { username: 'problem_user', succeeds: true },
  { username: 'locked_out_user', succeeds: false },
];

for (const loginCase of cases) {
  test(`login for ${loginCase.username}`, async ({ page }) => {
      await page.goto('/');

      await page.getByTestId('username').fill(loginCase.username);

      await page.getByTestId('password').fill('secret_sauce');

      await page.getByTestId('login-button').click();

      if (loginCase.succeeds) {
        await expect(page).toHaveURL(/inventory\.html/);
      } else {
        await expect(page.getByTestId('error')).toContainText('locked out');
      }
  });
}
```

The `LoginCase` type (Session 7) guarantees that every case has the exact required fields. A typo in `succeeds` is caught by TypeScript before the tests even run.
